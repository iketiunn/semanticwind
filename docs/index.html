Semanticwind

Semantic HTML when it’s enough. Tailwind when it isn’t.

A small semantic baseline for Tailwind CSS. Start with useful native HTML, then scale into Basecoat, Tailwind utilities, and product-specific components only when the interface asks for them.

2 · Basecoat component

Add component meaning when HTML semantics stop being enough.

A destructive button or a richer field is UI meaning. Basecoat owns that layer instead of smuggling variants into unrelated HTML attributes.

Shown publicly on the project page.

3 · Tailwind utilities

Use utilities for context, layout, and exceptions.

Component semantics stay in Basecoat. Page-specific choices stay obvious in the markup instead of leaking into global selectors.

Ready to publish?

4 · Your component

Promote repeated product concepts into product components.

Semanticwind should never learn what a device card is. Your application should.

The rule

Use the smallest layer that accurately expresses the UI.

semantic HTML
      ↓ not enough
Basecoat component
      ↓ needs local customization
Tailwind utilities
      ↓ repeated product-specific pattern
your own component

Would this style still make sense for almost every correct semantic use of this element?

If not, it probably belongs in a component or utility instead of Semanticwind.

Semanticwind is deliberately small. The escape hatch is the architecture, not another pile of selectors.
