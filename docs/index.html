Semanticwind

Semantic HTML when it’s enough. Tailwind when it isn’t.

A small semantic baseline authored with Tailwind CSS. Start with useful native HTML. Add utilities, a component layer, or your own components only when the interface actually needs them.

2 · Tailwind utilities

Use utilities when the change is local or contextual.

Layout, responsive behavior, and one-off emphasis belong in the markup. They do not need another semantic rule or a component abstraction.

Ready to publish?

3 · Component layer

Add component meaning when a pattern becomes reusable.

Variants such as destructive or outline are UI meaning, not HTML meaning. Use your own component classes or any component library you prefer.

4 · Product component

Promote repeated domain concepts into your own components.

Semanticwind should never learn what a device card is. Your application should.

The model

Escalate only for the reason HTML stopped being enough.

semantic HTML
      │
      ├─ local layout / visual exception ──→ Tailwind utilities
      │
      ├─ reusable generic UI ──────────────→ component layer / library
      │
      └─ repeated product concept ─────────→ your own component

Would this style still make sense for almost every correct semantic use of this element?

If not, it probably belongs in a utility or component instead of Semanticwind.

Semanticwind is deliberately small. The escape hatch is Tailwind and normal component architecture, not another pile of global selectors.
